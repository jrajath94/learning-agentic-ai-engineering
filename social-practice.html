Translate the demonstration into a contract

Choose one visible claim from a post. Write the input, output and check that would establish it. Record the source access you actually have. A full caption can describe a method. A runnable repository can expose how that method handles a failed call. A video can show a sequence, but its cuts may omit part of the attempt.

Use the worked projects as a local test environment. You can compare an agent's patch against the engineering fixture, compare retrieval settings against the held-out cases, or test a briefing retry. Their recorded outputs give you a reference before you adapt the method.

Keep the caption, the frame and the implementation separate

The public reels-to-md skill separates the post caption, transcript and images from the video. It uses transcript timestamps to locate the matching frames, then emits a guide and scripts. Those outputs can contain steps the assistant inferred. This study read the procedure and skipped its optional browser-cookie step. [DI01]

This separation matters when a reel claims that an agent can test a patch in parallel. The caption might name a product. A screen frame might show two terminal windows. Neither observation establishes that both commands tested the same source revision. Record each piece in a separate field. Find a primary artifact that settles the missing claim.

Check shared resources and replay boundaries

James Goldbach's indexed Reel description proposes separate worktrees. Boris Cherny's indexed Threads excerpt names --worktree. The Claude Code documentation confirms the separate checkouts. Another Threads excerpt raises resource pressure when several agents build at once. It supplies no timing data. [DI10] [DI11] [DI12] [DI16]

For the repository workshop, make both checks request port 4173 and separate checkout paths. The checkout names pass the Git isolation check. The port allocation fails. Give the second check port 4174 and a separate database or browser profile. Record the revision and runtime identity in each receipt. Measure one serial and one parallel run with the same inputs before you assume a time benefit.

Claude's indexed Threads announcement identifies dynamic workflows. The full product documentation explains one restart boundary. If a task fails in the middle of the observed sequence, a relaunch can reuse the completed prefix and repeat later tasks. A completed task after the failure can run again. [DI09] [DI13]

Use three local steps for a briefing. Collect source IDs, validate the records and prepare a draft. Set the saved states to complete, failed and complete. The relaunch plan reuses the source IDs and runs both later steps again. Give draft creation a stable key and check that the retry produces one committed draft. A step with a public side effect needs a recorded result and a duplicate check before it can safely repeat. Durable workflow workshop

Refresh a tool list when the application changes state

The Edits bridge author reports that a direct Claude Code connection kept the tools available at initial connection. The editor offered other tools after the author opened a project. The bridge checks the upstream list after a tool call, compares the names and emits notifications/tools/list_changed when the names change. The MCP specification documents that notification for servers that declare listChanged. [DI02] [DI03]

Build a fake server with two states. At home it exposes open_project. After the project opens it also exposes preview. Have a client save its first tools/list response. Omit the notification once. The client can open the project and still lack a usable preview tool. Add the notification and confirm that the second list adds preview.

Now use a harder case. Leave the name preview unchanged. Require a revision in the second input schema. Compare a list of sorted tool names with a digest of sorted tool definitions. The first misses this change. A local Python check verified that a digest over canonical JSON changed with the schema and stayed stable when the definitions were reordered. Isolate parallel code changes

Two coding agents can edit separate Git worktrees at the same time. A worktree gives each checkout its own directory and branch state. It does not prevent two changes from conflicting when they use the same contract or file. Git documents worktree operations. It makes no claim about agent quality. [DT04]

Use this example. Add a strict date filter to a billing export, then add a help page for that command. The help page can use the agreed input format. The filter needs its own code and tests. Give each task an owner and a bounded output.

BranchOwned pathsAcceptance evidence
agent/export-filterbilling/export.py and tests/test_export.pyCutoff, offset order, malformed row, no partial output
agent/export-helpdocs/export.mdExample command and output match the agreed contract
IntegrationReviewed changes from both branchesRun the documented command and the export tests

Before launch, agree on the date format, cutoff rule, output schema, and filenames. Create one worktree per owner. Record its branch, base commit, and allowed paths. Ask each agent to show the test command and result. Inspect both diffs before integration. Then run the acceptance checks on the combined result.

git worktree add -b agent/export-filter ../export-filter HEAD
git worktree add -b agent/export-help ../export-help HEAD
git worktree list

Use a clean base for both worktrees. Record the starting commit before either agent edits. Let the documentation task start after the interface is fixed, even if its files do not depend on the implementation branch. When both tasks finish, merge the code first. Read the help text against the merged command. Run the exact example from a clean checkout. Keep a separate test record for each branch and for the integration commit. This gives you three states to inspect: the initial baseline, each isolated result, and the combined result.

Do not split a change only because two agents are available. First list the files and decisions that each task needs. If both tasks need to choose the same data field, separate them only after one owner writes that field into the contract. If a test fixture changes the meaning of both tasks, give it one owner too. A review agent can still read both diffs without a second write branch.

The counterexample is two agents that both change billing/export.py. The first changes the timestamp from local time to UTC. The second adds a new filter against the old local-time contract. Separate directories do not resolve this semantic conflict. Assign one owner to shared interfaces. Run dependent work in order.

Three TikTok creators describe separate agents, parallel tasks, a shared backlog, and communication with a team lead. Those details explain the coordination model. They do not show that a coding team is faster or more accurate. Anthropic's report says parallel work fits broad independent research. It also warns that most coding tasks have fewer truly independent parts and that multi-agent runs use more tokens. Use parallel agents only when the acceptance checks can stay separate. Choose a subagent by measuring handoff loss

A subagent can handle a self-contained task in a separate context. It can return a short report while it keeps long logs or code searches out of the main session. A skill can instead load reusable instructions into the main context. These patterns solve different problems. Product documentation recommends a subagent for isolated work, restricted tools, or noisy output. It recommends the main conversation for quick edits and work that needs frequent shared context. [DT05]

A TikTok creator argues that one agent with a skill can be simpler than several specialists. The same creator reports an example where a consolidated support workflow omitted a shipping constraint. This is one person's report. The transcript does not show the test results. The useful lesson is to measure omissions before you remove a boundary. [DT03]

Use ten fixed requests from a repository task. Include a normal invoice, a surcharge, a tax exemption, a retry, and a duplicate record. Write the expected result for each request before the run. Compare the current specialist subagent with a candidate skill. Use the same model, tools, revision, and request text. Run each request twice in a fresh session.

InputExpected resultFailure to watch
Invoice with shipping surchargeKeep surcharge in the total and show its sourceSkill omits the charge after consolidation
Tax-exempt account with valid certificateApply exemption and cite the certificate fieldSubagent adds tax from a stale default
Duplicate invoice eventKeep one ledger entryEither workflow creates a second charge

Score every case for correctness, critical omissions, unsupported claims, tool calls, token use when exposed, and elapsed time. Keep per-case results. Do not rely on the total score. Stop if either workflow misses a critical invoice rule. Keep the subagent if it finds a defect that the skill misses. Accept the skill only if it matches or exceeds the subagent on every critical case with no added unsupported answer. If a run is missing or the input changes, report the comparison as inconclusive.

Store the expected answers outside the agent's working copy. Give each run a fresh branch or reset fixture so one workflow cannot learn from the previous result. A simple ledger can have one row per input, workflow, and run. Record the commit, prompt version, model name, test output, and scorer decision. Keep the agent's explanation beside its answer, but grade the answer against the fixed rule. Treat a faster result as a separate observation. It does not cancel a missed constraint.

This check is an adaptation of the creator's proposed ten known-answer requests with two runs each. It is not a benchmark result from TikTok. The protocol keeps its core idea and adds fixed inputs, a blind expected-answer set, and stop rules. A team, subagent, or skill needs one verified job. A large role chart is not an acceptance criterion. [DT03]

Close the loop with visible evidence

Keep each coding task short enough to inspect. State the input, expected state, allowed files, and test command. Ask for one change at a time. Review the diff, then run the same case that exposed the defect. TikTok's Effect House docs show a related loop: inspect the live preview and script logs, provide a screenshot when an element is wrong, then ask for one refinement. The docs also say the tool has limits. This is product guidance for Effect House, not a guarantee for general code. [DT07]

Keep a short run record with the base commit, changed paths, test command, result, and unresolved failures. If the agent returns a claim without a test result, leave it unverified. If a task needs shared state or frequent clarification, keep it in one session. If it has separate outputs and separate checks, test parallel work in isolated worktrees.
