Do not write "I ran the test" unless the terminal agrees.

Chris and Daniel, the day after they say the Claude Code source leaked. Transcript: practicalai.show/352/transcript. They are describing what they say they saw in that leak. This page does not copy the leaked source. The rule worth keeping is the one they state in their own words at about 23:09 onward.

See the shape first

Sequence and state

1. Mechanism, as they tell it

At 23:09 Daniel says the valuable part of these systems is the harness: how memory is handled, how tools connect, how a session wakes up, and how context is pointed at. He says the leak mattered because that harness can sit in front of other models, not because weights shipped.

He then describes three memory layers he says were in the leaked code. First, a memory.md that is always in context but is not the whole memory. Second, topic shards: an index plus separate files, loaded when the topic matches, so the window does not fill with unrelated notes. Third, a search path that checks logs with something like grep instead of trusting the model's own summary. At about 23:40 he states a write rule: the agent may say it is running tests while the run failed. Memory should record the event only after the environment confirms it. He also mentions an "auto dream" pass about every 24 hours that consolidates observations into durable facts for long-running agents.

None of that is an Anthropic doc. It is two hosts, one day after a leak, telling you what they think the code did. Treat the layer names as their report. Treat the write rule as a practice you can apply without their report being true.

2. Artifact

Do not reconstruct memory.md from this episode. The file you can use is kit/podcasts/practical-ai-verify-then-write.md. It appends one line, and only after exit code 0. That is narrower than the architecture they sketch, on purpose.

3. Sequence

  1. Pick a check that already exists: pytest tests/test_auth.py -q or the equivalent in the repo.
  2. Run the kit prompt. The first run should be a command you expect to fail, so you can see that the memory file does not change.
  3. Fix the one failure, or point the command at a test that passes.
  4. Run again. The memory file gains one line: date, command, exit 0.
  5. git diff should show that line and nothing the model "meant" to do.

4. Failure modes

  • The model writes the line and also a paragraph of intent. The prompt forbids that. If the diff has a paragraph, reject it.
  • Exit code 0 from the wrong command. true is exit 0. The command in the memory line must be the test, and you re-run it.
  • Using this episode's shard story as a schema for a bank memory store. They did not publish a schema. A secondhand layer diagram is not a design doc.
  • They also discuss anti-distillation decoys and a file they call uncover.ts. That is allegation about leaked code. It is not a feature to copy into your agent.

5. Exercise

In a throwaway clone, add a failing test that asserts 1 == 2. Run the kit prompt. Self-check: memory file unchanged, diff empty. Delete the bad assert. Run again. Self-check: one new line, and pytest of that file prints passed when you run it in a terminal the model is not driving.

6. Your stack

The write rule is harness-agnostic. Claude Code, Codex, Muse, and a Grok Bot skill can all be told to append a line only after a command succeeds. The memory file path changes: CLAUDE.md, AGENTS.md, or a project note you name. Do not point it at a production log that contains customers. For a research experiment, the line is a lab notebook entry. For an open-source PR, the line does not belong in the PR. It belongs in a gitignored local note, unless the project already documents that file.

Where this disagrees with the engineers on the other pages

  • Boris and Thariq talk about CLAUDE.md as instructions to the model. These hosts talk about memory as a log of what happened in the world. Mixing those into one file makes the model reread old command output as if it were policy.
  • Karpathy's loop records before and after scores because the metric is the product. This episode's rule records that a command happened. A score without the command, or a command without the score, answers a different question.
  • If Anthropic's actual code does not match the hosts, the write rule still stands on its own. The layer diagram does not.
