Grok and Grok Bot

The public record shows a proactive bot with a cloud computer, skills, routines, and per-tool permissions. It does not show a named engineer running a whole company through Grok, and it does not show an internal playbook.

What a regular chat user misses

  • A computer that stays up. xAI describes Bots as sharing a persistent cloud computer with a browser, filesystem, and terminal. Chat on a laptop does not keep that machine working after you close the tab. C01
  • A team of bots, not a longer prompt. The overview's picture is several bots handing work along, then bringing you a draft. C02
  • Skills and routines. Walk through a task once, save a skill, schedule a routine. The 1.2.3 notes add that a routine can read the earlier conversation in its chat, and that a signed-out connector skips the run instead of failing quietly in a half-finished way. Reconnect cards can also arrive as a Slack or Teams direct message. C03 C07
  • Permissions at tool grain. Connecting Gmail is no longer the whole decision. Send can be Needs approval while search is Always allow. C06
  • Connector before browser. If a site has a connector, the Bot is supposed to use it, or show the connect card, before it opens the browser. C08
  • Split memory. People and organizations, your profile, standing instructions, and projects are separate memories in the 1.2.3 notes. C08
  • MCP apps that do not auto-send. Clicking a message button inside an MCP App puts the text in the chat box for you to send. Each turn keeps its own MCP App card. C06

Three workflows that are actually written down

1. Inbox drafts that wait for you

Who: xAI, as a product example. No customer name.

  1. Connect Gmail.
  2. The Bot sorts overnight mail and drafts replies for threads that need you.
  3. Every draft stays for you to send.

The 1.2.3 permission model is the piece a careful user adds: search can be Always allow; send stays Needs approval. That pairing is this site's reading of two xAI pages together, labelled as synthesis in the tutorial below. C04 C06

2. Meeting notes to a Slack post

Who: xAI's Granola example.

  1. Each evening the Bot reads that day's Granola notes.
  2. It pulls action items with owners.
  3. It drafts a Slack post that goes out once you approve.

C04

3. A small bot team on a campaign

Who: xAI's handoff example.

  1. One bot's routine pulls the week's numbers.
  2. Another drafts a campaign from them.
  3. A third reviews it.
  4. They hand the result to you to approve, edit, or send back.

This is the closest public text to "a business running through Grok." It is still a vendor storyboard. No P&L, no founder, no prompt log. C02

How the product asks you to think

  • Show the work once, then schedule it. The skill is the program; the routine is the trigger. C03
  • Approval is part of the design of the published examples, not an extra you bolt on after a mistake. Drafts wait. Overheard never posts. C04 C05
  • Prefer a connector to a browser session when both exist. C08
  • Team admins can allowlist MCP tools, including the built-in GitHub connector, which the changelog says is off unless a rule allows it. The bot is supposed to say when an admin blocked a tool. C06

Strongest counterargument

Adversarial

Nothing in the fetched xAI pages shows an internal Grok engineer, a founder, or a finance lead running a company on Grok Bot. The "business" workflows are illustrations. A serious operator would ask for a named user, a month of logs, and a count of messages the bot sent without approval. Those numbers are not public here. Copying the campaign storyboard into a production inbox, with three bots and a shared computer, is an untested bet. See G02.

Tutorial · a routine that drafts and cannot send

Eight parts, as required. This is one bounded workflow, not a company operating system.

1. Original question

How do I get a Grok Bot to prepare replies and a Monday plan without it being able to send mail or post to Slack on its own?

2. Source-grounded facts

  • Gmail example: sort mail, draft, leave drafts unsent. C04
  • Calendar example: Sunday evening, flag clashes, send you a short Monday plan. C04
  • Each tool can be Always allow, Auto-review, Needs approval, or Blocked. C06
  • A routine with a dead sign-in skips until you reconnect. C07

3. Core concepts

A skill is the saved procedure. A routine is that procedure on a clock. A tool permission is the harness rule the model does not get to talk its way past. Memory is split, so a standing instruction ("never send") belongs in standing instructions, and the hard stop belongs on the tool.

4. Pattern and feedback loop

  1. Trigger. Sunday 18:00 for the week plan. Weekday morning for the inbox draft pass. You set the schedule; xAI says a repeated task becomes a routine. C03
  2. Execute. Read calendar and mail. Draft. Do not send.
  3. Verify. You read the drafts. The permission level Needs approval is the verifier for any send tool.
  4. State. If it drafted the wrong tone, correct it once and ask it to save the correction as a skill, which is the path the skills page describes. C09

5. Conflicts and misconceptions

The skills page's Grok 4.3 line and the changelog's 1.2.3 line are different objects: a model name and a bot app version. Treating either as "the current Grok" without the other is how version rumors start. Also, Auto-review is not the same thing as Needs approval. Auto-review lets xAI's checker decide whether you must see the action. Needs approval shows you a card every time. C06

6. Hypothesis unproven

Hypothesis

Setting read tools to Always allow and send tools to Needs approval will cut surprise outbound messages without making the morning draft useless. The changelog defines the four levels. It does not publish a study of that split. Test it for five weekday mornings and count drafts you actually sent unchanged.

7. When to use what

  • Use a Grok Bot routine when the work is outside the repo: mail, calendar, a deck, a recap.
  • Use a coding harness (Claude Code, Codex, Muse, Antigravity) when the artifact is a diff. Grok Bot's overview does not document a repo test loop.
  • Use Overheard when you want a quiet digest and an explicit never-post rule. C05

8. One bounded next action

Connect one mailbox. Set the send tool to Needs approval and the search tool to Always allow. Ask for one morning draft pass, not a standing routine, and send nothing the bot wrote until you have read it. If that single pass is useful, save it as a skill and only then attach a schedule.
