Gemini and Antigravity

Antigravity is Google's agentic coding surface: an app, a CLI, an SDK, and IDE extensions, with a changelog that moved weekly through November 2026. The power-user features in that changelog are multi-model orchestration, a swarm, Python workflows, and remote machines. A named Google engineer's diary was not found in this pass.

What a regular Gemini chat misses

  • Orchestrator. One prompt, two models. The 18 November note pairs Neon for planning with Hydrogen for implementation. Six days earlier the changelog described Orchestrator as pairing Hydrogen with Carbon. Read the date on the row you are copying. C23 C26
  • /swarm. Multiple subagents over a message board. By 17 November, business and enterprise accounts can open it when an admin allows it. C27 C24
  • Dynamic Workflows. The agent writes Python that fans work out, using a runtime shipped with the app, instead of you babysitting tabs. C25
  • /btw. A side question with read-only tools. The main agent keeps its context. This is the "ask without derailing" move. C25
  • SSH hosts. The app installs a remote server over OpenSSH using your ~/.ssh/config. Projects, worktrees, agents, and terminals run on the Linux host and keep working after you close the window. C24
  • PR pills and plugin marketplaces. Pull-request links become live status. The 17 November notes add partner plugins including Cloudflare, Grafana Cloud, SonarQube, incident.io, Better Stack, Tavily, and Levels.fyi. C24

Three workflows grounded in the changelog

1. Plan on the strong model, edit on the fast one

Select Orchestrator (Neon) after 18 November if you are on a plan that has Neon as default and you have not pinned a model. The changelog's description: Neon plans, Hydrogen implements. You still read the diff. The changelog does not say Orchestrator replaces review. C23

2. A long task as a message board

/swarm is the documented way to put several subagents on one long-horizon task, coordinating through a message board rather than a single context. Use it when the slices are independent enough to write down. The 17 November note is the gating line for business and enterprise admins. C27 C24

3. The repo lives on a Linux box

Connect an SSH host from the sidebar, the project menu, or the command palette. Antigravity installs its remote server. Agents and terminals stay on that machine. This is the closest documented analogue to "my laptop is not the build machine." C24

Engineering read of the November changelog

Google spent the month splitting roles that a single chat collapses: plan versus implement, main thread versus side question, local window versus remote machine, one agent versus a board of agents. That is graph thinking in product form. Parallel subagents help when the work splits. They hurt when every slice edits the same files, which is why the SSH note bothers to mention Git worktrees on the host.

Superpowers can be installed into Antigravity with agy plugin install https://github.com/obra/superpowers. The README says the using-superpowers skill description prompts the model to load it at session start. That is a community methodology on Google's harness, not a Google feature. C44

Tutorial · one swarm, then a side question

1. Question

How do I use Antigravity's November 2026 multi-agent tools on a task that has three independent slices, without losing the ability to ask a question mid-flight?

2. Facts

/swarm uses a message board. /btw is read-only and multi-turn as of 16 November. Orchestrator (Neon) is the 18 November default pairing. Dynamic Workflows are Python inside the app as of 13 November. C23 C25 C27

3. Concepts

A message board is shared state. A side question is a read-only branch of context. Orchestrator is a sequential handoff inside one trajectory. Dynamic Workflows are a program that can launch parallel calls. Those four are different shapes. Using all four at once on a first try is how you lose the plot.

4. Loop

  1. Trigger. A task you can split into slices that do not edit the same files.
  2. Execute. State the slices in the /swarm prompt. Let the board carry status.
  3. Verify. Ask a /btw question against the diff: which tests ran, which files overlap. Read-only means this check should not edit.
  4. State. Keep the swarm prompt in the repo as a note if you will run it again. The changelog does not describe a saved swarm skill.

5. Conflicts

Opening /swarm to business accounts on 17 November does not tell you whether a personal Pro account already had it on 9 November. The 9 November line announces the feature. The 17 November line is an admin gate for business and enterprise. If your seat is Google AI Pro, confirm in the product rather than assuming either sentence alone.

6. Hypothesis unproven

Hypothesis

Orchestrator (Neon) plus a human diff review beats Neon-only on chores and loses to Carbon-only on novel design. The changelog calls Carbon strongest for long-horizon work and Neon the default. It does not publish the crossover point. The Neon blog's benchmark numbers were deliberately left out of this hub.

7. Decision support

  • Single-file fix: one model, no swarm.
  • Several independent packages: /swarm or a Dynamic Workflow.
  • You need the beefy planner and you have Carbon: the 12 November Orchestrator wording. You are on the 18 November default: Orchestrator (Neon).
  • The code must build on a Linux CI-like box: SSH host.

8. Bounded next action

Pick a refactor with two packages that do not import each other. Run one /swarm that names both packages and forbids edits outside them. When it returns, ask one /btw: "which files changed in both slices?" Stop there. Do not add a Dynamic Workflow until that pair has worked once.
