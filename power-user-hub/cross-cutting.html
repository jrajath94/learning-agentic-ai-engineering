Parallel versus sequential

Sequential, on purpose

  • Superpowers: brainstorm, then worktree, then plan, then implementation, then review. The README forbids skipping ahead by calling the skills mandatory. C44
  • Boris: plan until he likes it, then one implementation pass. C22
  • Muse /plan then the rest. C35
  • Orchestrator: plan model, then implement model, inside one trajectory. C23

Parallel, on purpose

  • Several Claude sessions, separate checkouts. C22
  • pstack /arena (N attempts, keep the best parts) and /swarm (N workers, one report). C48
  • Antigravity /swarm on a message board, and Dynamic Workflows in Python. C27 C25
  • Dots dividing work among background agents. The launch post says this. It does not show the board. C29
  • Muse background agents that stay up for the session. C35
Rule of thumb, labelled synthesis

Parallelize slices that do not share files or a decision. Sequence anything where the second step's input is the first step's judgment. A swarm of agents editing one module is sequential work wearing a parallel costume.

Vibe coding, in the words of the people who named it

Karpathy, quoted by Simon Willison on 6 February 2025: accept all suggestions, do not read the diffs, paste errors back with no comment, and treat the result as fine for a throwaway weekend project. The padding prompt in that quote is in the vault as an example of the practice, not as a recommendation. C41

Willison, quoted by Ars Technica in March 2025: if you reviewed, tested, and understood the lines, that is an LLM used as a typing assistant. Vibe coding your way to a production codebase is, in his words there, clearly risky. C42

Anti-patterns that fall out of those two quotes

  • Accept-all on a repo you must maintain.
  • Pasting an error with no hypothesis, then shipping the workaround when the model cannot find the cause. Karpathy described doing that for weekend projects.
  • Calling reviewed, tested code "vibe coding." Willison's distinction is the useful one in an interview: say which you did.

Guardrails that are productized, not slogans

  • Claude: hooks and deny rules, branch protection, a human merge. C49
  • Superpowers: delete code that was written before the test. Verification before completion is a named skill. C44
  • pstack: reproduce first, and keep interrogate findings only when a run proves them. C48
  • Duet, dots, Grok: approval before outbound side effects. C12 C29 C06
  • Muse: plan approval, sandbox on from the first run, Contributor mode as an explicit data decision. C37 C38

A research pipeline: literature, synthesis, artifact

This hub is the worked example. The pattern is the one the source rules forced, and it matches how the coding skills tell an agent to behave.

  1. Literature. Fetch the origin page. A news article that repeats a launch is an echo, filed once. C50 C52 C51
  2. Synthesis. Write the sentence you believe, with the claim id. If you combined two pages, say so. The Grok permission-plus-draft tutorial does that.
  3. Artifact. A page, a ledger row, a failing test, or a plan. Meta's kernel loop and Boris's Chrome check are the engineering versions: the artifact is not the model's paragraph. C36 C22
  4. Gap. What you could not open goes in the gap report instead of into a smooth paragraph.

Pocock's /grill-with-docs is the coding-agent version of step 2: the grilling session also writes a glossary and ADRs so later sessions share the nouns. C43

MCP, as of the 28 July 2026 spec

David Soria Parra and Den Delimarsky describe a stateless core. The initialize handshake and Mcp-Session-Id are retired. Each request carries its protocol version and client info. Method and tool names travel in Mcp-Method and Mcp-Name headers so a gateway can route without parsing JSON. Server-initiated elicitation and sampling become Multi Round-Trip Requests: the server returns input_required, and the client retries with the answers. Dynamic Client Registration is deprecated in favor of Client ID Metadata Documents. Tasks move to an extension. Roots, Sampling, and Logging are deprecated with at least twelve months of runway. C39

HTTP authorization, when you implement it, is OAuth 2.1 with RFC 9728 protected-resource metadata and a bearer token on every request. A local stdio server should read credentials from the environment instead. C40

Speed and correctness

Lauren Tan's README states the trade in one line: if you want to go fast, go deep first, and the goal is less code rather than more. Parallelism is what she says you earn after one agent is verifiable. C47

Boris's version of the same trade: a slower, stronger model (he named Opus 4.5) needed less steering and so finished sooner than a smaller model. That is a January 2026 judgment about a model generation that has since moved. The shape of the argument is still the one Antigravity uses for Orchestrator: spend the expensive model on the plan. C22 C23

Caveman's README is the cost side. The author reports that a "be concise" instruction already captures most of the output saving, and that ultracave goes further, on a small sample he labels as not yet re-run for a later rules version. Read those numbers as his measurements. C46

Hypotheses unproven

H1 · three proactive agents, one inbox

Duet, a dot, and a Grok Bot on the same mailbox will double-draft and occasionally double-send the moment any one of them is set looser than Needs approval. Each product documents an approval stop. None of them documents coexistence with the other two.

H2 · cross-family review

A review panel drawn from three families, as in pstack's default, catches more merged bugs than a second pass by the author model. The README prescribes the panel. It does not include a public benchmark.

H3 · one planner

Installing Superpowers and Pocock's skills and pstack together lowers the quality of plans, because three routers disagree. Each author describes a different relationship to "the process." The interaction is unmeasured.

Tutorial · ship one verified change this week

1. Question

What is the smallest stack, using only practices published by the toolmakers and the skill authors above, that takes a bug from report to a diff I am willing to merge?

2. Facts

Specific bug prompt and a failing test (Anthropic). Separate checkout if anything else runs (Boris). Closer instruction file wins, keep it short (Özen on Codex, or CLAUDE.md on Claude). Reviewer that did not write the code (Anthropic subagents, or pstack interrogate). Human merge (Anthropic). C19 C22 C49

3. Concepts

See the principles page for the harness model. You need one trigger, one executor, one verifier that is not the executor, and one place the lesson is written down.

4. Worked loop

  1. Pick the harness you already know. Do not install a second one for this exercise.
  2. Write the bug as symptom, path, and test, using Anthropic's shape even if the harness is not Claude.
  3. If you use Codex, put the test command in the nearest AGENTS.md. If you use Claude, put a one-line project fact in CLAUDE.md only if the code does not already show it.
  4. Let it implement. Open the diff yourself. Run the test yourself.
  5. Ask a second session, which has not seen the first transcript, to try to break the fix. pstack calls this interrogate and tells it to keep only what a run proves. You can do a poor man's version with any second model: "here is the diff and the test command; try to falsify the fix."
  6. Write one sentence into the instruction file about whatever the second session found, or about a mistake you do not want repeated.

5. Conflicts

Superpowers would insert a design document and a worktree before step 2. That is right for a feature and heavy for a one-line bug. The README's own sequence is the full methodology. Use the full sequence when you do not yet know the design. Use the short loop when the design is the existing code and the bug is local.

6. Hypothesis

H2 above. Run the second session twice, once on the same model and once on a different family, and keep a tally for ten bugs. Until you have the tally, you do not have evidence.

7. Decision support

Feature with an unclear design: Pocock /grill-me or Superpowers brainstorming, then the loop. Bug you can reproduce: this short loop. Overnight unattended work: Boris's sandbox note and pstack's autonomous-run playbook exist; both still require a verifier. Do not start there. C22 C47

8. Bounded next action

One bug. One harness. One failing test you watch fail. One diff you read. One sentence written back into the instruction file. Stop.
