Spend the effort on the first pass, and write down the fix he skipped.

Thariq Shihipar, Anthropic, on latent.space/p/thariq. Timestamps below are the speaker labels in that page's transcript. The show notes above the transcript are Latent Space's summary. Where those notes and his lines differ, his lines win.

See the shape first

1. Mechanism

At 00:15:37 he says short prompts work when the person already has a model of what Claude can one-shot. The skill is that model, not a longer spell. At 00:21:52 he says a lot of cap burn is "undo this and redo it" after a design the model could have gotten with more context on the first turn.

Effort is a harness knob that buys more verification. At 00:23:49 he says higher effort spends more tokens checking, and that a stronger model can sometimes finish a simple task in fewer tokens because it does not need to re-verify. At 00:25:24 he gives the split he used in a blog post: code review and security at high or max, UI at low or medium, and more care when you are building an API and need edge cases. At 00:26:01 he says he looked at about 70 Terminal Bench problems. The common high-effort failure is not ignorance. The model thinks of the right move and then does not take it. Implementation notes are how you see that fork.

2. Artifact

He does not read a JSON config on this episode. The replicable piece is the prompt in kit/podcasts/thariq-effort-and-notes.md. At 00:28:10 he says Anthropic is going to support AGENTS.md, that keeping different files per model is painful, and that in the limit CLAUDE.md goes away. He thinks it can be better to start a project with no CLAUDE.md, and to add a line only when a failure repeats. Those lines change when the model changes. Swyx, at 00:27:38, says Thariq has a documented dislike of AGENTS.md and asks if it is going away anyway. Thariq's answer is yes, they will support it.

3. Sequence from the episode

  1. 00:15. Write the prompt for Claude as the audience. Know what it one-shots in this repo before you ask for a redesign.
  2. 00:21. If you are about to say "undo that", stop. The usage went into the redo. Put the constraint in the first prompt instead.
  3. 00:25. Pick effort from the task. Do not leave a security review on the UI setting.
  4. 00:26. Ask for implementation notes before you accept the patch. Read the option it considered and dropped.
  5. 00:28. If that dropped option is correct, tell it to do that one. If the same miss happens again on this model, add one line to CLAUDE.md. If you switch models, re-check that line. He says the failure list does not transfer cleanly.

4. Failure modes

  • Max effort on a CSS tweak. He says that spends tokens on verification you can see is unnecessary ("you don't need to spin up Chromium").
  • Low effort on a review. His split puts review at high or max. A low-effort "LGTM" is the failure the split is for.
  • A long CLAUDE.md full of one-off scolds. He says start without one, and add a line for a repeated failure. A file of stale model-specific bans will fight the next model.
  • Notes that only say the model "thought hard". The useful note names the fix it rejected. If that sentence is missing, ask again before it edits.

5. Exercise

Take an open PR in your repo. Run the kit prompt with task type review and no edits. Self-check: the notes name one change the diff does not contain, and you can decide whether that change should exist. Only then say go. If you cannot find a skipped option, the notes are too vague. Run it once more with the test command in the prompt.

6. Your stack

This episode is Claude Code effort levels and CLAUDE.md. Codex reads AGENTS.md. He says they will support that file because models differ and maintaining two files hurts. On a bank repo, put the repeated failure in the file the harness actually loads, and do not put customer rows in either file. Muse and Grok Bot are not given an effort table here. Do not copy "high or max" onto a product that has no such switch. Use the same idea: a review gets more checking than a label change, and you pay for the checking.

Where this disagrees with Boris

Boris, on 2 Jan 2026 and again in the team practice he described, keeps a shared CLAUDE.md and adds a line when Claude does something wrong. Thariq, at 00:28:10, says a new project may be better with no CLAUDE.md, and that the file should shrink toward zero as models stop repeating the old misses. Both are adding lines from failures. They disagree on the default: Boris starts with the file. Thariq starts without it.

Boris round-robins plans across tabs. Thariq's 00:21 warning is that a bad first prompt turns into a redo loop that eats the cap. Use Thariq's notes when you have one hard task. Use Boris's tabs when the tasks do not share files and each prompt already has a test command.
