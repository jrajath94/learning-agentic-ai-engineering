Choose one study below. Open its guide and the original evidence together. Start with the example input. Write down the result you expect before you read the implementation. Follow the input through each function, request, file or decision. Stop when you can point to the line or rule that explains the result.

Use a table with one row per transition. Keep input, state before, state after and evidence in separate columns. Add the source revision or read date. If the code corrects your prediction, preserve both versions of the prediction. The correction shows exactly what you learned.

Each guide has a worked trace, a counterexample, a transfer task and three questions. All worked cases use synthetic data. The links open the original evidence. Open a study to read the full exercise. Download the Markdown worksheet to keep your answers next to the trace.

Prove the mechanism on a different fixture

  1. Run the worked trace by hand before you write code.
  2. Replace the model or server with fixed test responses.
  3. Record the input, first decision and observed result.
  4. Change one field that should produce a different result.
  5. Check whether the predicted change occurs at the expected step.
  6. Answer the three questions with the source closed.
  7. Reopen the source to correct any answer you cannot support.

If you can predict only the demonstrated case, change when a result arrives or remove one required field. A lesson is complete when you can explain where the first observable difference occurs. Keep the output from the passing and failing cases. A partner should be able to reproduce each from the fixture and the trace.

Pair the studies by what could break. For model decisions, trace the planner before you compare tool contracts. For state changes, trace a restart before you grade the outcome. For optimization, check the accepted examples before you calculate the cost of the run. Finish each pair with one counterexample that the first version accepted by mistake.
