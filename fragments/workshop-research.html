Research workshop: decide whether to replace a retriever

Keep the baseline. The revised retriever finds more evidence on development queries. It drops a required inspection card on a held-out query. You will reproduce both results and decide which evidence supports each decision.

Build the retrieval stage of a retrieval-augmented generation system, or RAG system. A RAG system selects source material for a model to use in its answer. Here, the code stops after source selection. It uses no language model, web search, embeddings, credentials, or network access. It tests a question that you can answer independently of generation. Did the right evidence reach the next stage within the available space?

Work in workshops/research/ inside the extracted guide. Use Python 3.8 or later. The commands in this section use python3. Use py -3 on Windows if that is your Python command. The local run sheet lists all files. Read the first three steps before you open the held-out result if you want to practice the decision yourself.

1. Write the comparison contract

Imagine a manual index for seven fictional product families. An operator enters a short phrase such as Kite feed blockage. The retriever can return two document cards. Each card has a unique ID, a title, a body, and a source family. The family identifies documents that describe the same product. The source family serves the split audit. The ranker cannot filter on it because the user enters only query text.

A label names a card that contains evidence for the query. Label every relevant card in the fixed corpus before you score a query. For D01, the query gives no jam location. Both the tray and exit instructions apply. For D05, the query names the exit. Only the exit procedure applies. The labels specify which evidence the operator needs. They do not grade the prose of a possible answer.

2. Score two rankings by hand

For D01, underline kite, feed, and blockage. Those are the three baseline query tokens. The tokenizer splits on characters outside ASCII letters and digits and converts text to lowercase. It returns a set, so repeated words count once. Score one point per distinct query token in the body. Ignore zero scores. Sort by descending score, then ascending ID. Read the first two IDs.

The baseline returns K01 and K02, both with two points for kite and feed. The reference set is K11 and K12. The intersection of the returned IDs and reference IDs is empty. Recall is the number of hits divided by the number of reference IDs. Precision at two slots is the number of hits divided by two. Both values for this baseline query are 0/2.

For the combined candidate, add jam because the glossary maps blockage to jam. Give two points to each matching title token. Keep one point per matching body token. The title of K11 contains kite and jam. Its body contains jam. Its total score is 1 + 2 × 2 = 5. K12 receives the same score. The tie rule puts K11 first. 3. Make the split and detect leakage

Separate questions by the family that owns the reference. Development uses Kite, Moss, Reed, and Frost. Holdout uses Birch, Lark, and Finch. The development and held-out labels cannot share a relevant document ID. The same index remains searchable in all runs because the experiment asks whether new queries can find evidence in an existing index. In one development trace, the baseline returns a Birch card for a Kite question. That cross-family error is valid evidence about a shared index.

A different question requires a different split. To measure retrieval for products absent during development, keep those source families out of the development index as well. Make a development index from the development families. Add the held-out documents only when the frozen system indexes the assessment corpus. Record whether the system may build IDF statistics, embeddings, or dictionaries from that new index. Each permission changes the question the test answers.

Run the normal audit and the deliberate leak. The deliberate leak exits with code 1. A paraphrase of D05 keeps the Kite family and K12 reference under a new query ID. A random row split or duplicate-ID check alone can miss that leak. The workshop audit catches shared query IDs, family IDs, and reference IDs. It cannot identify a manual copy that has a new family ID. Group copies, translations, and revisions by provenance before you split real data.

python3 -B run.py audit
python3 -B run.py audit --holdout-file leaky-holdout.json

The standard audit checks six development cases and three held-out cases. A trusted operator can run that validation before tuning. In a real evaluation, the developer receives only the development rows. The operator records a digest of the held-out labels in the plan before the first trial. The local files remain readable for study. Access control in a production experiment must keep the test labels and results outside the candidate's workspace.

6. Read the implementation behind a research claim

Start with Autoresearch's program.md. Its protocol keeps the measurement code fixed, changes train.py, captures process output, and records decisions separately from raw logs. The instructions describe a repeated loop and preserve an improved commit. Read what an operator delegates and which file stays fixed. DR01

Then inspect train.py. The training loop times synchronized GPU steps and adds to the measured budget after initial steps. After the break, it calls evaluate_bpb and prints both training time and total elapsed time. The initial work and final evaluation therefore need separate accounting. This workshop borrows the fixed comparison idea. It measures four candidate attempts on a CPU and does not run those GPU experiments. DR02

Read the metric implementation in prepare.py. Its evaluation function obtains validation batches, masks zero-byte targets out of the summed token loss, and divides by the byte total and log(2). The resulting bits per byte is a different quantity from document recall. A reproducible experiment names the evaluated population, numerator, denominator, and measure of cost. DR03

Anthropic Engineering separates the trial transcript from the outcome of a task. It recommends a clean start for a trial and deterministic graders when they fit. Apply that distinction here. The token hit trace explains rank order. The reference ID intersection decides the score. For a tool-using assistant, the trace can show a claimed update while a state read determines whether the update occurred. DR04

OpenAI's BrowseComp release uses brief reference answers for questions that require search. In the public implementation, BrowseCompEval.__call__ supplies the question to the sampler and keeps the reference for a later grader. This is a useful boundary to inspect in any eval. The inspected branch also has a parser inconsistency. grade_sample returns the full match correct: yes, while its caller checks for yes. A fixture that feeds a known correct verdict through both paths can expose that mismatch. This static observation does not establish which code produced the paper's results. DR05 DR06

OpenAI's document Q&A example separates context metrics from answer judgments. Follow that separation if you add generation. A correct answer can come from prior model knowledge after retrieval fails. A wrong answer can follow good retrieval. Capture the retrieved source IDs and the answer verdict independently. The workshop's thresholds come from the local task contract. DR07

7. Adapt the experiment to your documents and agent

Pick a workflow with a verifiable evidence requirement. For an internal methods library, ask Which document specifies the exclusion rule for protocol A? Define evidence as the current section that states the rule. Treat superseded versions and protocols for other instruments as test negatives. Use a synthetic copy while you develop the harness. Keep private source files outside any external adapter.

  1. Assign stable IDs to source sections. Keep the document family and revision in separate fields.
  2. Label common, ambiguous, unsupported, and critical questions. Include the reason and reference for each positive label.
  3. Split by document family or the unit that produced the question. Keep revisions and paraphrases together.
  4. Freeze the baseline configuration, labels, metric, guardrails, and budget. Record a hash for each file.
  5. Score a few fixed cases by hand. Include an empty list and a multi-reference case.
  6. Change one setting per candidate where possible. Run an ablation when two changes interact.
  7. Inspect paired traces. Preserve missed IDs, extra IDs, and the score denominators.
  8. Freeze the chosen candidate. Give the held-out comparison to the test owner.

If your system uses chunks, decide whether the grader credits the entire document or a specific span. A document ID can look correct while the selected chunk omits the rule. Store a stable chunk ID and a parent document ID. Deduplicate parent IDs if the metric measures documents. Count multiple required spans when a query needs evidence drawn from distinct parts. Make those choices before you inspect candidate outputs.

If you add a model, freeze its exact version, tool schema, prompt, timeout, and available sources. Give it the question and a search tool. Require an ordered list of evidence IDs. Keep reference labels on the evaluator side. Validate returned IDs and represent tool errors separately from empty results. Then add a distinct answer check for evidence support, issue type, and refusal when evidence is missing. Use independent trials for a model whose outputs vary. Record both the number of trials and the fraction of successes. Keep the same retrieval budget so a larger context cannot masquerade as a better ranker.

The model adapter protocol gives a request, a response schema, and a filled example. It is an optional design exercise. No model adapter or online evaluation ran for this workshop. To repeat the supplied result, run only the local Python files.
