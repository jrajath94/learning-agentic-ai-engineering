Turn a lesson into your own workflow

Use one real task, a small evidence packet and an acceptance test you can explain.

Start with an input you can inspect

Use a small task from your own work after you complete one workshop. A concrete input and an expected output give the agent something to test. For example, use one retrieval query that cites an archived document. The first result should be a failing case you can reproduce on demand.

This route assumes you can read Python and use a terminal. Each workshop explains the state and transition before it introduces the implementation. Use the supplied fixtures first. Then replace one fixture with an approved example from your project and predict which result will change.

The local programs run without a model account. They expose the mechanics behind the agent workflow. The prompt files let your chosen agent perform the same bounded tasks against your own repository. Live model outputs depend on that agent and require the same checks.

Read, predict, run, then change one thing

Reading a finished solution can hide the decisions that created it. Start with the supplied failure. Write the expected output before you run the command. If your prediction differs, identify the first state transition that explains the difference. This makes the next edit causal.

  1. Read the contract and inspect one fixture.
  2. Predict the output and the state after the first operation.
  3. Run the baseline command in the workshop.
  4. Compare each transition with your prediction.
  5. Apply the smallest repair that restores the stated invariant.
  6. Run the original case and a neighboring case.
  7. Hide the reference and reconstruct the core function.
  8. Change one assumption and explain the new failure before you repair it.

In the automation workshop, the invariant is one stored result for one operation identity and source fingerprint. A crash after commit leaves a result even when the caller sees a timeout. Predict the retry from the database state. Then change the source while retaining the operation identity. That second case tests whether your design can detect stale work.

Checkpoint question and worked answer

A process logs “started” before it writes a draft. It then crashes. Is the draft present? The log alone cannot answer. Inspect the transaction and the stored draft. A record of intent establishes that the operation began. A committed result establishes that the write completed. A safe retry uses the stored state and the task's identity rule.

Use learn-by-reconstruction.md for an interactive session. The prompt asks the tutor to wait for your prediction. Use the exercise answers only after an attempt. Save your first incorrect transition in a short note so the next session starts at the actual gap.

Give the agent a small evidence packet

A useful packet tells the agent what to inspect, what result counts and how to verify it. Begin with a task file, the relevant input fixture, the current entry point and the test command. Add a file when it answers a specific unresolved question. This keeps irrelevant context from displacing the decisive evidence.

Download the complete archive to retain the folder structure. The project starter explains each editable file. Its retrieval example uses invented documents. Replace the paths and rules after you inspect your own checkout.

Keep the task state separate from stable repository instructions. A checkpoint records what happened in this attempt. Repository instructions record facts that apply across attempts. Mixing them can make an old failure or temporary restriction appear to be a permanent rule.

Use the prompt files at a decision point

Open a prompt file in your editor or attach it to your coding agent. Fill the inputs before you execute it. Give the agent the named repository and fixture. Read the requested output before you permit a dependent step. The files use ordinary language, so their contracts apply across agent interfaces.

For a concrete engineering attempt, start with repository orientation. Then write acceptance cases, reproduce the bug and request a patch. Give the final diff and the original contract to a fresh reviewer. If the reviewer finds a defect, repair it and rerun the affected checks. Save the final revision beside the result.

Use parallel work where the outputs can be checked

Give each worker an output it can own. Discovery can map the call path while another worker inspects the input schema. Implementation depends on their findings. A reviewer then needs the final patch. Running all three at once can create opinions about different revisions.

Inspect two independent source filesYes, if both workers use the same revisionEach returns function names and evidence for its claims

The supplied budget is an example of a bounded attempt. It permits six model calls and one explicit escalation reason. Change those limits to fit your task. Record real usage only when the agent reports it. An unknown token count stays unknown. The usage chapter explains the published lab figures and the difference between counts, concurrency and API price estimates.

Prove you can use it without the worked answer

Use the recall schedule after the first run. On the next day, reconstruct the transition from its contract. Three days later, change one assumption. After one week, use the same invariant on a small task from your repository. These intervals are a suggested routine you can adjust.

DimensionObservable passRepair if it fails

PredictionYou predict a new boundary case before executionLocate the first wrong transition in the table

TransferYour project has its own inputs, acceptance cases and evidenceReduce the adaptation to one input and one output

Save one short checkpoint when you stop. State what you observed, what you still cannot explain and the next action. A later session can then begin with the unresolved mechanism.
